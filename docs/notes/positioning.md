# 创新性与差异化

> 用途:① 写作品材料时的定位口径;② 决定下一步该做什么(见 §5);③ 避免与已有工作撞车。
> 引用纪律:只与 `docs/notes/related-work.md` 中"已核实"的工作比较。

## 1. 一句话

PhaseWeaver 不改造推理引擎,而是把 **Agent 的执行生命周期**变成推理资源的控制面:
用"阶段"驱动"租约",用"租约"表达"对某段 KV 的处置权",并把这件事做成**引擎无关、可断言、可恢复**的机制。

## 2. 与最近的邻居的差异

| | Tokencake(已读摘要) | Continuum(已读摘要) | 本项目 |
|---|---|---|---|
| 落点 | 推理**服务层**:改调度器与内存管理器 | 引擎侧 KV TTL | **编排层与引擎之间的运行时** |
| 信号 | 引擎内部队列/显存 | 时间 | **Agent 阶段**(推理/工具/等待)与工具进程状态 |
| 决策粒度 | 引擎内请求 | 请求 | **执行单元树**(Agent/Subagent/工具调用) |
| 可移植性 | 绑定引擎内部 | 绑定引擎内部 | **能力协商的适配器**(mock / OpenAI 兼容 / vLLM) |
| 失败处理 | 未强调 | 未强调 | 不变量 + 树形回收 + 上下文压缩降级 |

我们不主张"让工具等待期的 KV 让出 GPU"这件事本身是新的——那是 Tokencake 已经做过的。
我们的主张在**控制面的位置**与**语义的完备性**上。

## 3. 四个具体创新点(按可辩护程度排序)

### P1 子 Agent 树的资源语义(最强)

公开工作里通常把"请求"当作调度单元;我们的调度单元是**带父子关系的执行单元树**,并给出:
- fork 时父单元**先 park 再进入 `WAITING`**(不变量 I1 的直接后果),子单元才能真正拿到容量;
- `SHARE`(共用全局预算)vs `ISOLATE`(子树硬配额)两种资源继承模式;
- 超配额时**压缩上下文后降级运行**而不是简单拒绝或打死父任务;
- join 时把子树的用量与重算成本合并记账,树形回收保证不泄漏。

这套语义目前没有找到对应工作(待继续检索确认)。实验已给出:L1 下扇出场景 p99 −23.7%,
贪婪子场景 SLO 1.000 vs 0.875。

### P2 "处置权"租约 + 能力协商(强)

租约不是"借一块显存",而是"对某段 KV 的处置权 + 该处置的代价":
`RETAIN / OFFLOAD / DROP / RELEASE`,由适配器声明能力,不支持时**显式降级**并在事件里记录
`degraded_from`。这让同一个运行时可以横跨"有 KV connector 的 vLLM""只有 OpenAI 接口的服务"
"纯模拟器",而不需要为每个引擎写一套逻辑。

### P3 把"让出"写成不变量(中)

`phase ∈ {ACTING, WAITING} ⟹ context ≠ ACTIVE`,`context ∈ {ACTIVE, RETAINED} ⟺ 持有租约`。
把架构口号变成可被 property test 与 CI 持续验证的断言,并暴露了多个真实缺陷
(如 `RETAIN` 时误释放租约、释放顺序导致的检查器窗口)。这是工程上的差异化,不是算法新意。

### P4 事件日志作为唯一事实来源(中)

所有指标由日志重放得出,不维护并行计数器;第二阶段(检查点/幂等回执)无需重构内核。
这条本身不新(事件溯源是成熟范式),新在**把它用在"Agent 执行状态 + 推理资源状态"的联合追踪**上。

## 4. 不能声称的

- ❌ "首次提出工具等待期让出 KV Cache"——Tokencake 已有,且更深入引擎内部。
- ❌ "推理快 X%/省 Y% 显存"——目前只有 mock 仿真(L1/L2),没有真实 GPU 数据。
- ❌ "支持任意引擎"——目前验证到 OpenAI 兼容接口与本地假服务;vLLM 只做了适配器与能力声明。

## 5. 据此确定的工作优先级

1. **补强 P1**:子 Agent 语义是唯一"没有邻居"的点,应继续做实验(不均衡 SLO、嵌套 fork、join 合并记账的正确性)。
2. **坐实 P2**:M5 已把适配器做出来,下一步是用真实引擎跑通一次(需要 GPU → 已提 issue)。
3. **P3/P4 保持**:作为工程质量指标持续做,不作为卖点单独宣传。
4. 不再投入:K3 成本模型(B2c 负结果)、更复杂的调度算法(与 P1/P2 无关)。

## 6. 检索待办

- 确认 vLLM 之外(SGLang radix cache / HiCache)的等价能力,以支撑 P2 的"跨引擎"说法。
