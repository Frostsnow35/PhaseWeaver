把 Agent 的工具阶段
变成可编程的显存决策

PhaseWeaver 位于编排层与推理引擎之间,接管执行单元的 KV 资源生命周期。

一个 Agent 回合通常是「推理数秒 → 工具数十秒 → 再推理」。工具执行期间 GPU 空闲, 但该 Agent 的 KV Cache 仍占着显存,其他 Agent 只能排队;而引擎的调度器看不见这段相位, 只能按显存压力被动驱逐。

PhaseWeaver 把相位切换做成显式接口:保留、卸载、丢弃、释放四种处置权以租约形式 发放,父子 Agent 之间的 KV 以单次不可中断的所有权移交完成。本文给出机制、不变量、 以及确定性仿真下的实验结果——这些数字不是真实 GPU 测量,证据等级标注为 [L1]。

1问题

对单卡部署的 Agent 服务来说,显存通常比算力更早成为瓶颈。原因不在于并发不够, 而在于并发被“占住”了:一个 Agent 调工具时,它的 KV Cache 仍完整驻留在显存, 引擎对此没有任何处置权;新的请求只能等待,或由引擎按 LRU 粗暴驱逐,导致之后重新 prefill。

现有两种做法各有代价。把长工具 Agent 的并发压到很低,会让 GPU 在工具间隙长时间空转; 完全交给引擎的 prefix cache 与驱逐策略,则无法区分“马上要回来”和“半小时后才回来”的上下文。 两者的共同问题是:没有人把“这段上下文接下来会被怎么用”告诉资源层。

由此确定三条设计目标:资源决策必须以相位为依据,而不是以显存水位为依据; 决策必须可撤销、可降级,不能假设引擎一定支持换出;父子 Agent 之间重复的 prefill 必须能被消除。以下三节分别对应这三条。

2设计

2.1 两条正交的状态机

执行阶段(Phase)与 KV 归属(ContextState)被拆成两个独立维度。 前者描述“它在做什么”,取值包括排队、推理、执行工具、等待、终态;后者描述“它的上下文归谁、 在哪儿”,取值包括未建立、活跃、保留、已换出、已丢弃、已释放、已移交。

正交带来的是可断言性:七条不变量在每次状态变更后检查,例如活跃的上下文必须持有租约、 终态单元不得残留租约、移交期间所有权唯一。违反任意一条, 测试会立即失败,而不是等到显存泄漏才被发现。这条约束在本项目里抓出过两个高危缺陷: 交接异常路径上的记账泄漏,以及进程回收器把“查询失败”误判为“进程已消失”。

2.2 处置权租约

租约表达的不是“我已经分配了这么多显存”,而是“这段上下文允许被怎么处理”。 四种处置权分别是保留(维持驻留)、卸载(移动到主机内存)、丢弃(释放显存、保留可重算的元数据)、 释放(彻底结束)。调度器只负责给出处置建议,由运行时与引擎协商后执行。

引擎能力不足时,协商结果是显式降级:例如没有 KV connector 的引擎收到“卸载”时, 实际执行“丢弃”,并在事件里记录 degraded_from。这一点比“假装支持”重要—— 否则调度器会基于不成立的前提做决策,压力越大错得越多。

2.3 父子之间的 KV 移交

当一个 Agent 把任务分派给子 Agent 时,子通常需要父的完整上下文。默认做法是子重新 prefill, 代价与上下文长度成正比;本项目的做法是把 KV 的所有权从父移交给子, 子零 prefill 起步,汇合时再交回。

移交只有一次挂起点:引擎调用返回后,租约转移、句柄交换、上下文状态变更在同一段同步代码里完成。 若租约无法随块转移(预算不足或隔离配额已满),块会交还给原主,子退回重新 prefill—— 宁可慢,也不留下“占着显存却没有租约”的中间态。

2.4 可证下界

调度器需要一把尺子。对单卡、每 Agent 交替「推理 r 秒、工具 t 秒」的工作负载, 设备平均并发存在结构上限 c̄ ≤ k·r/(r+t)(k 为显存可容纳的并发流数), 由总工作量即可推出 makespan 下界 T ≥ W / A(c̄_max)。它不能证明某个调度器最优, 但能回答“还有多少结构性空间”:仿真中该差距在 2 GiB 下为 3.7%,4 GiB 下为 8.4%。

3实验

结论集中在两类收益上。其一是消除重复 prefill:嵌套委托的重算量从 35 200 降到 16 853 tokens(−52%),扇出场景从 81 195 降到 61 099(−25%)。其二是尾部延迟: 编排场景 p99 从 133.4 s 降到 104.0 s(−22.0%),委托场景从 71.3 s 降到 56.6 s(−20.6%)。 两组数据都在多 seed 下零失败。

并非所有策略都值得保留。我们曾假设“错开工具阶段”能抬升瞬时并发,并实现了按推理槽位准入的 对齐策略。异构工具场景下,基线 goodput 为 0.1065,对齐策略只有 0.0215,且 6/24 个任务因等待 准入超时而失败。原因与 2.4 节的下界一致:平均并发由每个 Agent 自身的 r/t 比例决定, 对齐只能改变瞬时重叠,改变不了上界;在容量已经足够时再加闸门,只会制造排队。 该策略保留在仓库中作为对照,默认关闭。

关于“最优”。项目不声称调度器最优。下界只说明还有多少结构性空间(2 GiB 下 3.7%), 以及在给定工作负载族里最优能到哪一步。

4工程

运行时对正确性的依赖程度很高:一次状态错位就可能表现为显存泄漏或任务卡死。因此工程约束 与机制同等重要。所有指标由事件日志重放得出,不维护第二套计数器;同一 seed 两次运行的指标 逐位一致,实验可复现。

可观测性走“事后分析”路线,运行时零开销:事件落盘后重放为相位时间线与单测归因, 能直接回答“这个任务为什么慢”,并把耗时归因到推理、工具、排队、等待四类之一。

扩展点是四个协议,不是基类:引擎适配器、调度策略、工具执行器、场景配置。第三方包通过入口点 注册即可接入,import phaseweaver 不会加载任何插件;插件损坏时抛出的错误会指明 是哪个插件、哪个组。交付闸门把“测试、静态检查、双平台类型、确定性、可观测性、性能回归” 串成一条命令,CI 之外还有本地可验证的达标线。 

# 第三方后端:一个零参工厂 + 一行入口点声明
[project.entry-points."phaseweaver.backends"]
my-engine = "my_pkg.engine:build_backend"

# 使用时按名解析,自动切到真实时钟
async with PhaseWeaver(backend="my-engine", profile="research") as pw:
    await pw.run("task", agent)

5边界

  1. 真实 GPU 验证缺失。 适配器(vLLM / OpenAI 兼容)已实现,但没有 [L3] 实测数据。本文所有加速数字 都不得表述为真实引擎性能;这也是当前最主要的交付风险。
  2. autopilot 不是万能最优。 它是安全默认值:所有场景零失败、SLO ≥ 0.944,但编码场景略逊于基线, 检索场景不如固定 B2。系统因此暴露“场景档案 + 策略组合”,而不是假装存在单一最优配置。
  3. 仿真规模有上限。 虚拟时钟已改为事件驱动(16 agents 提速 6.6×),但更大规模实验仍建议 控制在 12 个 Agent 以内,否则墙钟主要由仿真器而非模型行为决定。
  4. 已登记的技术债。 租约容量等待仍是定时轮询,在真实时钟下应改为事件通知;多机调度不在范围内。
